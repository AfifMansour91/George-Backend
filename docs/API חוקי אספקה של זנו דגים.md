# **API חוקי אספקה של זנו דגים**

גרסה 1.1.0, אוקטובר 2026\.  
ה-API מחזיר את חוקי האספקה של האתר: לאילו ערים יש משלוח, מה דמי המשלוח והמינימום בכל אזור, אילו תאריכים וחלונות שעה פתוחים, עד איזו שעה אפשר להזמין כל חלון, ואילו מוצרים מוגבלים. כולל גם את הקטלוג.  
כל הקריאות הן GET חוץ מאחת, ואין בו נקודת קצה שכותבת משהו לאתר. מה שלא נמצא בו: לקוחות, הזמנות ותשלום. מחירים, מלאי ומשקלים כן מופיעים, אבל הם מסונכרנים לאתר מהמערכת האחורית, ולכן משקפים את הסנכרון האחרון ולא בהכרח את הרגע הזה.

## **חיבור**

כתובת הבסיס:  
https\://zano-dagim.co.il/wp-json/oc-shipping/v1  
כל בקשה צריכה את הכותרת X-Api-Key עם המפתח שקיבלתם. עובד גם Authorization: Bearer. מפתח שנשלח ב-query string מקבל 401, כי מפתח בתוך URL נשמר בלוגים של השרת ובמטמוני proxy.  
curl \-H "X-Api-Key: \<KEY\>" https\://zano-dagim.co.il/wp-json/oc-shipping/v1/version  
כתובת http מקבלת 301 ל-https ולא מחזירה נתונים, אבל המפתח של אותה בקשה ראשונה כבר עבר ברשת בגלוי. כדאי לפנות ישר ל-https.  
המגבלה היא 120 בקשות לדקה למפתח. מעבר לזה חוזר 429 עם כותרת Retry-After. גם ניחושי מפתח חוזרים מאותה כתובת IP מגיעים ל-429, אבל מפתח תקין לא נחסם בגלל זה.  
בתיקיית התוסף באתר יש openapi.yaml עם כל נקודות הקצה והסכמות, לייבוא ל-Postman או לכלי דומה.

## **השדה order\_by**

כל חלון אספקה שחוזר מ-/availability מגיע עם order\_by, שהוא הזמן האחרון שבו אפשר להזמין את החלון הזה. חותמת זמן מלאה עם אזור זמן:  
`GET /availability?city_code=70`

`{`  
  `"days": [`  
    `{ "date": "2026-10-06", "weekday": 2, "slots": [`  
        `{ "start": "08:00", "end": "20:00",`  
          `"order_by": "2026-10-06T16:00:00+03:00",`  
          `"order_by_reason": "cutoff_time",`  
          `"order_ahead_days": 0 } ] },`

    `{ "date": "2026-10-08", "weekday": 4, "slots": [`  
        `{ "start": "00:00", "end": "12:00",`  
          `"order_by": "2026-10-07T17:00:00+03:00",`  
          `"order_by_reason": "cutoff_time",`  
          `"order_ahead_days": 1 } ] }`  
  `]`  
`}`  
בשורה השנייה המשלוח הוא ביום חמישי, אבל הזמן האחרון להזמין אותו הוא ברביעי ב-17:00. ככה זה עובד בחלק מהאזורים.  
מאחורי השדה יש ארבעה חוקים שונים באתר, והמוקדם שביניהם הוא זה שנכנס לשדה. order\_by\_reason אומר איזה מהם קבע:

> * cutoff\_time: שעת החיתוך של אותו יום. כש-order\_ahead\_days הוא 1, החיתוך ביום שלפני.  
> * preparation\_time: זמן ההכנה שהחנות צריכה לפני תחילת החלון. בזנו 60 דקות.  
> * window\_closes\_early: חלון שנשאר פתוח גם אחרי שהתחיל, אבל נסגר מספר דקות לפני סופו. באשדוד, למשל, החלון הוא 08:00 עד 20:00 וביום ראשון הוא נסגר ב-14:00.

השדה מחושב מאותם חוקים שהקופה של האתר עצמה מפעילה, ונבדק מול הקופה: דקה לפני ה-order\_by האתר מציע את החלון, דקה אחרי כבר לא. כלומר השוואה בין השעה הנוכחית לשדה הזה מספיקה כדי לדעת אם החלון עוד פתוח, בלי קריאה נוספת לאתר.  
ה-offset הוא חלק מהערך. שעון הקיץ מתחלף בתוך 30 הימים שה-API מחזיר, ולכן אותה שעה מקומית יכולה להיות שני זמנים שונים.  
תאריכים שלא מופיעים ב-days הם ימים שהחנות סגורה בהם, תאריכי חג שנחסמו, או תאריכים מעבר ל-30 יום. הם לא חוזרים עם דגל, הם פשוט לא ברשימה.

## **נקודות הקצה**

| מה | מחזיר |
| ----- | ----: |
| GET / | רשימת נקודות הקצה. נוח כבדיקת חיבור ראשונה. |
| GET /version | rules\_version, מחרוזת שמשתנה בכל שינוי בחוקי האספקה או בהגבלות המוצר. התשובה היא בסביבות 80 בתים. לא משתנה בעדכוני מחיר ומלאי שוטפים. |
| GET /meta | אזור זמן, מטבע, מספור ימי השבוע, והנוסחים שהאתר עצמו מציג ללקוח כשמוצר הוא איסוף בלבד, כשהסל מתחת למינימום, וכשהכתובת מחוץ לאזור. |
| GET /areas | שבעת אזורי המשלוח: דמי משלוח, מינימום, לוח הזמנים, ימים סגורים ותאריכים חסומים. בלי רשימת הערים, כי באזור אחד יש 1,096 ערים. |
| GET /areas/{id} | אזור בודד. |
| GET /cities | 1,136 ערים, עם עימוד וחיפוש. כאן קוד עיר הופך למזהה אזור. סך הכל בכותרת X-WP-Total. |
| GET /cities/{code} | עיר אחת, עם דמי המשלוח והמינימום שחלים עליה בפועל. לעיר יכולים להיות ערכים משלה שדורסים את האזור. |
| GET /pickup-locations | סניפי איסוף עצמי. בזנו יש אחד. לאיסוף יש לוח, תאריכי סגירה וזמן הכנה נפרדים מהמשלוח. |
| GET /pickup-locations/{id} | סניף בודד. |
| GET /availability | החלונות הפתוחים כרגע עם order\_by. פרמטרים: city\_code למשלוח, או method=pickup עם location\_id. אופציונלי: product\_ids. |
| GET /products | הקטלוג, 125 מוצרים מפורסמים, עם ההגבלות מוצמדות לכל מוצר. modified\_after לסנכרון מצטבר. |
| GET /products/{id} | מוצר בודד. מקבל גם מזהה של וריאציה. |
| GET /products/restrictions | רק טבלת ההגבלות, 23 שורות ובסביבות 3KB. |
| POST /quote | בודק סל וחלון נבחר מול האתר. לא כותב כלום, זה POST רק כי רשימת מוצרים לא נכנסת ל-query string. |

## **הגבלות מוצר**

לכל מוצר יש אובייקט restrictions, גם ב-/products וגם ב-/products/restrictions:

| שדה | משמעות |
| ----- | ----: |
| pickup\_only | המוצר מסומן באתר כאיסוף עצמי בלבד. |
| pickup\_only\_except\_areas | מזהי אזורים שאליהם המוצר כן נשלח על אף הסימון. מערך ריק אומר שאין חריג. תמיד ריק כשהשדה הקודם הוא false. |
| delivery\_weekdays | הימים בשבוע שבהם המוצר ניתן לאספקה. מערך ריק אומר שאין הגבלת ימים. |
| lead\_days | ימי הכנה מראש. 0 אומר שאין. |
| is\_reviewed | האם מישהו בניהול האתר בכלל קבע את חוקי האספקה של המוצר. ההגבלות נרשמות ביד, ומוצר חדש מגיע בלי רשומה. false אומר שלא נקבע כלום. |
| has\_restriction | true כשאחת ההגבלות מגבילה משהו בפועל. |
| applies\_from\_product\_id | המוצר שממנו נקראה ההגבלה. שונה ממה שביקשתם כשביקשתם וריאציה, כי ההגבלה רשומה על מוצר האב. |

שני השדות הראשונים עובדים ביחד. התשובה לשאלה אם מותר לשלוח מוצר לעיר מסוימת היא:  
`!pickup_only || area_of(city) in pickup_only_except_areas`  
כאשר area\_of(city) הוא ה-area\_id שחוזר מ-GET /cities/{code}. קריאה של pickup\_only לבדו תחסום משלוחים שהאתר מאשר.  
המקרה שקיים כרגע באתר: קרפצ'ו טונה, מוצר 17745, מסומן איסוף עצמי בלבד ובכל זאת נשלח באשדוד, שהוא אזור 35\.  
`GET /products/17745`

`{ "restrictions": {`  
    `"pickup_only":              true,`  
    `"pickup_only_except_areas": [35],`  
    `"delivery_weekdays":        [],`  
    `"lead_days":                0,`  
    `"is_reviewed":              true,`  
    `"has_restriction":          true,`  
    `"applies_from_product_id":  17745 } }`  
פיש אנד צ'יפס, מוצר 40384, מסומן איסוף עצמי בלבד בלי חריג, ולכן pickup\_only\_except\_areas שלו ריק.  
כרגע באתר 23 מוצרים עם הגבלה: שניים איסוף בלבד, אחד מהם עם חריג אחד, ו-22 עם הגבלת ימים. אין מוצרים שדורשים ימי הכנה.

### **אותו חישוב מצד האתר**

כששולחים product\_ids ל-/availability יחד עם city\_code, כל מוצר חוזר עם deliverable\_to\_city, שהוא אותו חישוב כבר מוכן. מוצר שלא ניתן לשלוח לעיר מרוקן את רשימת הימים ומוסיף שדה blocked:  
`GET /availability?city_code=7700&product_ids=17745`

`{ "days": [],`  
  `"blocked": { "reason": "not_deliverable_to_city",`  
               `"product_ids": [17745] },`  
  `"products": [ { "product_id": 17745,`  
                  `"deliverable_to_city": false, ... } ] }`  
אותה בקשה עם city\_code=70, שהיא אשדוד, מחזירה את כל הימים בלי שדה blocked, ועם deliverable\_to\_city: true.  
deliverable\_to\_city מופיע רק כשיש עיר בבקשה. ב-/products וב-/products/restrictions הוא לא קיים, כי הם לא מתייחסים לכתובת מסוימת.  
איסוף עצמי לא מושפע מ-pickup\_only בשום מצב. /availability?method=pickup ו-POST /quote באיסוף לא חוסמים על השדה הזה.

## **מוסכמות בשדות**

| שדה | הערה |
| ----- | ----: |
| city\_code | מחרוזת אטומה. באתר יש שלושה סוגי קודים: למ"ס (70), Google place id (ChIJq6Zr1wFSHBURr\_qN5bQ\_gdo) ו-hash (641ad108627d8bbfcf1ec6dea525bcd2). אין התאמה לפי שם עיר, צריך את הקוד. |
| weekday | 0 הוא יום ראשון, 6 הוא שבת. בכל שדה של יום בשבוע בכל נקודות הקצה. גם ב-/meta. |
| date | YYYY-MM-DD. |
| start, end | HH:MM בשעון מקומי של החנות, Asia/Jerusalem. |
| order\_by | ISO 8601 עם offset. |
| min\_order | נמדד מול הסל אחרי הנחות ולפני דמי המשלוח. 0 אומר שאין מינימום. |
| max\_orders, max\_products | null אומר שאין תקרה לחלון. באתר לא מוגדרות תקרות כרגע. |
| scheduling\_type | weekly הוא לוח שחוזר לפי ימי שבוע. dates הוא רשימת תאריכים קבועה, ואז delivery\_weekdays ריק. |
| עימוד | X-WP-Total ו-X-WP-TotalPages בכותרות התשובה. per\_page נחתך ל-200 גם אם מבקשים יותר. |

## **שגיאות**

| קוד | מתי |
| ----: | ----: |
| 401 | מפתח חסר, שגוי, בוטל, או נקרא מכתובת שלא הורשתה לו. ההודעה זהה בכל המקרים. |
| 400 | חסר city\_code, location\_id או date. |
| 404 | עיר שאינה באזור משלוח כלשהו, או מזהה שלא קיים. |
| 429 | מעל 120 בקשות לדקה למפתח, או ניחושי מפתח חוזרים מאותה כתובת. יש כותרת Retry-After. |
| 503 | תוסף המשלוחים באתר לא פעיל. |

POST /quote מחזיר 200 גם כשהבדיקה נכשלה. התוצאה נמצאת ב-ok והסיבות ב-problems:  
`{ "ok": false,`  
  `"problems": [`  
    `{ "code": "date_unavailable" },`  
    `{ "code": "slot_unavailable",`  
      `"data": { "open_windows": [ ... ] } },`  
    `{ "code": "pickup_only_products",`  
      `"data": { "product_ids": [40384] } },`  
    `{ "code": "below_min_order",`  
      `"data": { "min_order": 450, "gap": 30 } }`  
  `] }`  
כש-pickup\_only\_products מופיע, date\_unavailable ו-slot\_unavailable לא מצטרפים אליו. לסל חסום אין ימים פתוחים, ושגיאת תאריך הייתה מצביעה על המקום הלא נכון.

## **ביצועים**

בין 1.2 ל-1.35 שניות לכל נקודת קצה, חציון של חמש מדידות מחוץ לרשת. רוב הזמן הוא טעינת וורדפרס, ושכבת הנתונים עצמה לוקחת בין 2 ל-110 מילישניות. הקבלה של עשרות בקשות לא תשפר את זה.  
גדלי תשובות: /version 79 בתים, /products/restrictions 3KB, /availability 4.8KB, /areas 8.9KB, /cities?per\_page=100 27KB, /products?per\_page=50 46KB.

## **מה שאין ב-API**

אין נקודת קצה שיוצרת הזמנה ואין אפשרות לכתוב שום דבר לאתר. ההזמנה, התשלום והסליקה לא עוברים דרכו.
